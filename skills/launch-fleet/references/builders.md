# Builders

Read this for a `start`, `reconcile start`, `check start`, `resume` or `reconcile resume` line, a refused probe, or a Claude plan-limit restart. The builder brief is `python3 -I scripts/brief.py builder <ticket repo>#<N>`, with the ticket's tracker repository as OWNER/NAME.

## 3. Builders

**Starting one** (a `start` line):

1. **Claim it.** Post `launch-fleet: starting` on the ticket with `post.py comment`, which prints its id. Then ask the check whether your claim stands: `sh "<this skill's folder>/scripts/fleet.sh" claim <N> <your comment's id>`. It reads the ticket afresh and prints `go #<N>` only when no older claim is still live (`starting`, `started` or `start checked`), no builder is recorded, no pull request is open, the ticket is still on the frontier, and its ready label was last put on by a maintainer with no edit since (#1448). Anything else (`withdraw #<N>: <why>`, or an error): edit your claim to `launch-fleet: start withdrawn`, and stop. Two ticks that overlap can't both start a builder: the older claim wins, and it keeps the ticket as you edit it to `started` and `start checked`.
2. **Start it,** checking `openwiz-bench route --json` first when `openwiz-bench` is on `PATH`: class `small` for an exact `polish`, `huntr` or `proposal` label and `build` otherwise, using `routing.<class>.spawn` — or `explore.spawn` on every `explore.every`th start of that class when `routing.<class>.explore` is set, so the other model stays measured — in place of `ops-starts.py flags`. If `openwiz-bench` is missing or its read fails or refuses, fall back to the flags `python3 -I "<this skill's folder>/scripts/ops-starts.py" flags --repo <owner>/<repo> small_builder` prints for an exact `polish`, `huntr` or `proposal` label, otherwise `flags --repo <owner>/<repo> builder` (the Models table's Small builder or Builder, read from the default branch at this start; the older `## Builder for small tickets` or `## Builder` without one); a failed read never blocks a start, and reviewer and fixer starts are unchanged. Pass the ticket in its title, and the one-line brief `brief.py builder` prints, the same for every builder:

   ```sh
   room-cli thread spawn --top-level --provider <harness> --model <model> --reasoning-level <effort> \
     --title "#<N>: <ticket title>" \
     --prompt "$(python3 -I "<this skill's folder>/scripts/brief.py" builder <ticket repo>#<N>)"
   ```

   Everything about the work is in the ticket and its spec, so the brief never drifts from them. A top-level thread starts from the default branch on GitHub, and outlives this tick. A fleet thread starts it as its own child instead (`--parent-self --project "$ROOM_PROJECT_ID"` in place of `--top-level`), so it can reach it (SKILL.md, "Fleet threads").

   With a host chosen (`host.py which` prints `host: <name>`), start it through that host's driver instead ("Hosts", below); `host: none` keeps the `room-cli` start above.

   **With a Roster** ([roster contract](../../../contracts/roster.v1.md), OpenWiz #1854): when `docs/agents/fleet.md` on the default branch has a `## Roster` section, `host.py roster` prints `roster: each start goes to its picked entry's driver` (`roster: none` without one; `which` still prints only the host setting), and every start goes through `host.py start <owner>/<repo> <N> <harness> <model> [SKILL] --row <row>` with the harness, model and row `ops-starts.py host --repo <owner>/<repo> <start>` prints for that start (the same start name as `flags`), never `room-cli` directly: `--row` is the Models row the selector really picked, a fallback included (a review on the `Builder` row when the Reviewer row is the builder's family, a fixer on the `Reviewer` row when the Fixer row is not the builder's family); the host setting is not read for starts. `host.py` takes the role from the skill (`build-ticket` is `builder`, `review-ticket` is `reviewer`, `launch-fleet` is `orchestrator`), picks the first entry in table order whose Roles hold that role (a `harness` entry only when its Name is that harness, `Claude Code` or `Codex`), starts it through that entry's driver, saves the role with the run, and runs the token step as `<role>-<N>` for the ticket's repository, the same for every entry and kind. **Effort** (#2594, driver v1's E4): `host.py` reads the Effort cell of the Models row `--row` names (a row that follows Builder uses Builder's), lowercased, so `Medium` is sent as `medium`; that row must start the given harness and model, and it must be one the role's starts can pick: `Builder`, `Small builder`, `Fixer` or `Reviewer` for a builder or a reviewer, `Orchestrator` for a fleet thread (`refused: the Models table's <row> row does not start ...`, `refused: --row <row> is not one of the <role> role's Models rows: ...`). A Roster start without `--row` starts nothing (`refused: a Roster start needs --row, naming the Models row its harness and model were picked from`): `host.py` never guesses a row from the harness and model, as two rows can name one model at different efforts. With an effort set, it reads the driver's `version` first: when its `can` lists `effort`, the start carries `"effort": "<effort>"`. When `can` leaves it out, nothing is sent or started; when the driver refuses the start with driver v1's effort refusal (`next` exactly `this host can't set effort: remove the effort for this harness in your Models table or Roster to run it at the host's default`), nothing is started and the start is never tried again, with or without the effort. Either way the line is `stopped (driver can't set effort): the <driver> driver can't run <harness> at <effort> effort`: `host.py` has written your fleet status note as `stopped (driver can't set effort)` and posted one `launch-fleet: driver can't set effort` comment, each only once and never with the driver's own words (a refusal's are in `driver-failures.log`, as for a failed start). Edit the claim to `launch-fleet: start refused: driver can't set effort`; the start waits until the Models table's Effort for that role is removed or the Roster gives the role an entry whose driver can set it, never another effort, and the next success clears the comment as a failed start's is. With no Effort column or a blank Effort cell, the start is exactly as before, with no `version` read; an Effort that isn't one plain word (`refused: the Models table's Effort for ...`) starts nothing, and a `version` answer that isn't driver v1's exactly stops with exit 2. `started #<N> on <driver> as <name> via <person>, <model name> <effort> effort` names the entry's label and the effort the start carried (`<model name> default effort` when the Models table sets none): write that `as ...` text in the `launch-fleet: started` claim, so the label is on the record. These exit-1 lines start nothing: `roster: no entry may take the <role> role with <harness>` and `roster: driver v1 can't start <harness> <model>; choose another model in the Models table` mean the start waits (edit the claim to `launch-fleet: start refused: <that line>`, never another entry or model); `Roster refused: ...` means the Roster breaks the contract, so withdraw the claim and report the line to the orchestrator as a `look`, never falling back to the host setting or `room-cli`; `refused: the Roster gives no role to the <skill> skill` and `refused: a Roster start needs --row, ...` are refusals to report the same way. With no `## Roster` heading, every start is exactly as before: `host.py` reads no Effort and no `version`, and the `room-cli` start passes the effort with `--reasoning-level`. A start writes `#<N>`'s shims only once it is going ahead, so a refused start never changes a running agent's, and each role's shims have their own folder, `agent-token-bin/<role>/<owner>/<repo>-<N>`, so no two repositories or roles share one.

**The token step** ([token-service contract](../../../contracts/token-service.v1.md), OpenWiz #1846): this step applies only while the App identity is on, and nothing turns it on yet ([identity.md](identity.md), OpenWiz #2394). **With the App identity off, a configured token service changes nothing:** no agent runs `scripts/github-app/agent-token.py` or any part of this step, even where a brief or a start still asks for it (until OpenWiz #2396), and every GitHub command runs as today's account. With the App identity on and a token service configured (`OPENWIZ_TOKEN_SERVICE` set and non-empty), every brief `brief.py` prints ends by telling its agent to run each GitHub command through the agent helper, `scripts/github-app/agent-token.py`, as `builder-<N>` (a reviewer as `reviewer-<P>`, a fleet thread as `fleet-<S>`, a tick as `fleet-tick`), over HTTPS only, and that approvals, repository settings and pushes that change `.github/workflows/` stay on the owner's login. `host.py start` and `wake` first run the helper's `start` for `builder-<N>` and pass on only its stderr. The driver's input stays as driver v1 has it, but its environment gains `#<N>`'s own `gh` and `git` shims first on `PATH` (in `agent-token-bin/` beside `LAUNCH_FLEET_RUNS`), so the builder it starts runs every `gh` and `git` call through the helper's `run` as `builder-<N>` in its own environment. A shim hands the helper the command's name, never a resolved path, so the helper's git guard runs and git gets the token only through the helper's credential helper, never as `GH_TOKEN`. The shims ask for the fleet's repository only, so a driver builder's call to another repository is refused by GitHub as the App's. A push that changes `.github/workflows/`, an approval or a settings change through those shims is refused by GitHub as the App's: the owner does it on their own login. With the App identity on, `loop.sh` runs each wake inside the helper's `run` as the read-only `fleet-check`; with it off, `loop.sh` never runs the helper. When the helper gets no token, it says so once on stderr and the work goes on as the owner's login. On fallback the helper uses its own HTTPS request to revoke any token it still holds. If GitHub does not revoke it, the helper retains it in an owner-only `kept-*.json` file for a later attempt. Preserve the private folder and its files. To revoke explicitly, run `agent-token.py revoke` with the same `--requester`, `--repository` flags and `--read` setting used for `start` or `run`. Within a wrapped run, a private revoke-only socket lets the helper revoke the matching token held in memory even if the private folder is unavailable. The socket returns only a revocation outcome. The helper runs only `gh api`, `cache`, `issue`, `label`, `pr`, `release`, `repo`, `run`, `search`, `status` and `workflow` with the App's token and stops any other gh command, so the brief says to run those without it; it also refuses to run at all while `OPENWIZ_GITHUB_APP_KEY` is set beside a configured service. The service is then the only App-token route: `OPENWIZ_GITHUB_APP_KEY`, the superseded key secret, is removed when `host.py` or `loop.sh` starts (first in a bundle's bootstrap), before either runs any child, and from each shimmed call, and [identity.md](identity.md)'s mint block is not used; with the App identity on, give a fleet's loops and agents the service's settings, never that secret. With no service configured, briefs, starts and wakes are exactly as today. Nothing asks for the App's key, and no token goes in a brief, record, log or argument.

3. **Record the outcome** by editing your claim (`post.py edit`): `launch-fleet: started` (when routed, keep line 1 exactly `launch-fleet: started` and put `routed: <model>` on line 2, e.g. `routed: neon`) when CloudRoom started it, or `launch-fleet: start refused: <its reason>` when it said no. A refused start stays on the frontier, and is tried again 10 minutes after the refusal (the edit that made your claim one), not sooner: the refusal's record is itself one of GitHub's messages, which would otherwise wake a retry at once, again and again. If the start timed out or you can't tell, leave the claim as it is: the check asks for a reconcile after 10 minutes.

**Hosts** (#1371). A project chooses where its builders run in `docs/agents/host.md` on its default branch: one `Host: <name>` line naming a driver in OpenWiz's `adapters/` (records v1, section 6). `host.py` reads it at the default branch's current tip on origin, never the checkout's copy, which can be older. Onboarding writes it, and the user changes it by asking their agent to edit that line; nothing else changes. `scripts/host.py`, run from the project checkout with `LAUNCH_FLEET_HARNESS`, `LAUNCH_FLEET_MODEL` and `LAUNCH_FLEET_SKILLS` set to your own `--harness`, `--model` and `--skills` for `status.py` (set them if you can; with any unset, a start or wake still runs and still comments, and only the fleet status note is skipped, with a warning naming them), calls the driver (`$OPENWIZ_ADAPTERS/<name>/driver`, driver v1) and keeps each run privately in `LAUNCH_FLEET_RUNS`, an absolute JSON file beside `LAUNCH_FLEET_STATE`, never in the checkout or a public record:

- **Start:** `read -r harness model row` from `python3 -I "<this skill's folder>/scripts/ops-starts.py" host --repo <owner>/<repo> <start>` (the start you chose above: `builder`, `small_builder`, or `fix_round_for_claude_builder` or `fix_round_for_gpt_builder` for a fresh round), then `python3 -I "<this skill's folder>/scripts/host.py" start <owner>/<repo> <N> "$harness" "$model" --row "$row"`: the harness `claude` for Claude Code or `codex` for Codex, the model the table's `--model` value and the Models row that start was picked from. Keep that row privately with the run: its review's same-family fallback starts on it ([reviews.md](reviews.md)). `started #<N> on <host>` means the run is saved locally: commit that run map to the private repository's latest map and read it back, as with the thread map, before you edit the claim to `launch-fleet: started`; a later wake restores it (SKILL.md, "Each wake" step 1). `unknown: #<N> started on <host> but its run was not saved; save run ...` names the run: save exactly that into the private map before anything else. `stopped (driver start failed): ...` means the driver refused three tries, 1 and 2 seconds apart (#1446): `host.py` has already written your fleet status note on the ticket as `stopped (driver start failed)` (unless the three variables were unset) and posted one `launch-fleet: driver start failed` comment, each only once. The comment never quotes the driver: it gives a fixed reason, `exit 1: refused` and the entry of the owner-only log `driver-failures.log` beside `LAUNCH_FLEET_RUNS`, which holds the driver's own `error` and `next`; read that entry to see what to do, and never copy it to GitHub. Post nothing more about it; edit the claim to `launch-fleet: start refused: driver start failed`. A line ending `; unknown: the ticket's report is incomplete (...)` is the same refusal: the note and the comment are each tried, and the parentheses name what failed; the next refused try writes what is missing. The next start or wake that succeeds marks that comment cleared and posts a `done` fleet note; a second line `unknown: the failure report on #<N> was not cleared ...` after a success leaves that to the next success. The `next:` on host.py's own line is the driver's text only when it holds no credential, private id, machine path or URL with user info (`user@` or `user:password@` before the host, with or without a scheme); otherwise it is withheld whole. `unknown: ...` leaves the claim as it is: the reconcile looks for the builder's status note and branch on GitHub before any retry, as a run may exist. A ticket never gets a second live run.
- **Wake:** every message to a builder with a run (a CI failure, findings, a resume) is `host.py wake <owner>/<repo> <N>`, after its record or reason is on GitHub: the builder reads its ticket and pull request again. Due lines name such a builder `thread run:<N>`. `woke` is the delivery's confirmation. A wake is retried and reported as a start is: `stopped (driver start failed): ...` means the delivery failed and the ticket says so; leave the message undelivered. `no run: ...` means the builder was started with `room-cli`: tell it as before.
- **Stop:** `host.py stop <owner>/<repo> <N>` when its ticket closes, in place of archiving its thread, then save the run map privately again.
- **No run map:** a due line `look #<N>: the private run map LAUNCH_FLEET_RUNS was not restored ...` or `... no private run map LAUNCH_FLEET_RUNS was restored` means this wake skipped the restore: restore it and read again; never guess the builder.

Wake and stop reach the host that started the run, even after the setting changes; the next start uses the new host. A driver gets the caller's environment unchanged, and no login ever passes through `host.py` or a driver. For a builder with a run, `reconcile start` and `check start` look for its live builder status note and its branch on GitHub instead of a thread. `host.py start OWNER/NAME N HARNESS MODEL [SKILL]` defaults to `build-ticket`; for a non-CloudRoom review, pass the pull request number and `review-ticket` as the skill (see [reviews.md](reviews.md)).

**Never wait awake.** No brief or message from a tick asks an agent to stay awake while it waits: a builder or reviewer never keeps a background watcher, a poll loop or a `sleep` waiting for CI, a review or another thread, and ends its turn instead, as `build-ticket` and `review-ticket` say. The tick's next message (CI failed, findings, a re-check, a resume) is what wakes it. A message that tells one to wait for something (#B to merge, say) says to end its turn until the resume (Jake, the cheaper-factory grill, CF1).

**One probe per batch.** Before claiming, read each `start` ticket's labels and pick its builder table, as step 2 above says: that is its assignment, and the starts with one assignment are one group. Claim them all as in step 1; then start that group's first claim alone, the probe. If CloudRoom starts it, start the rest of the group in parallel. If it refuses the probe for a reason that is not that ticket's own (the model catalog, the account or plan, the provider), edit the probe's claim to `launch-fleet: start refused: <reason>`, and every other claim of the group to `launch-fleet: start not tried: #<probe> was refused: <reason>`, without starting them. Each waits the same 10 minutes as a refusal, so the group retries together, with one probe again. A refusal for the ticket's own reason ends only that start: the next claim becomes the probe. Never swap in another provider or model.

**Claude plan-limit restart (#1196):** if the small builder (`ops-starts.py flags --repo <owner>/<repo> small_builder`) still selects `claude-code`, the tick prints `look: fallback builder is the limited family` and saves no fallback record; wait for an approved setting from another family before restarting. Otherwise, a Rust tick `restart` due item records `launch-fleet: builder fallback due, branch <branch>` on the ticket and names the small-ticket builder settings. Reconcile that recorded item before acting: never start twice. Stop/archive the limited builder, preserve its branch, then start the replacement from that branch using `ops-starts.py flags --repo <owner>/<repo> small_builder`, with the ticket brief and an explicit instruction to continue its existing work. Keep the old and replacement identities, the fallback claim, the branch and their handover lineage exclusively in private state; update the private builder mapping to the replacement after its start is confirmed. Update the original public checked-start record to `launch-fleet: start checked, branch <branch>`, keeping the same branch. The fallback comment keeps its branch-only first line, with no replacement identity appended. The private handover retires the old stored builder when the tick next reads it. It retains the original code on the branch, so the tick leaves the builder family conflicting for new reviewer assignments. First and fresh reviews print `look` and start no reviewer; the orchestrator or Jake chooses the reviewer explicitly. Never apply this fallback to a reviewer; its review waits for its family. A consumed fallback is never tried again automatically; an uncertain restart goes to the orchestrator.

**Reconciling** (a `reconcile start` line): before any retry, find out whether a builder started. Look for a thread titled `#<N>:` in `room-cli thread list`, and for its branch (`git ls-remote origin 'refs/heads/room/<N>-*'`). If one is there, edit the claim to `launch-fleet: started`. If not, edit it to `launch-fleet: start failed: <why>`, and the next tick starts it again. A ticket never gets two builders.

**Checking** (a `check start` line): its thread exists and is working, its title names the ticket, and its branch shows up. Then edit the claim to `launch-fleet: start checked, branch <branch>`. If the thread is gone or never started work, edit it to `launch-fleet: start failed: <why>`.

A builder stays with its ticket through every review round, and is archived when its ticket closes. It is never given another ticket.

**Waiting on another ticket (#467):** whoever tells an existing builder to
wait for #B, including the orchestrator answering a builder's question, must
also add a new `launch-fleet: waiting for #B` comment on its ticket. Post it
even when the answer uses free-form prose such as "Once #B has a verified
merge, continue." The latest wait replaces the previous one. The check also
reads the legacy first line `Orchestrator (PC, ops): **wait for #B.** ...`,
with or without the parenthesized context, an optional `yes, ` or `confirmed: `
lead-in (comma or colon accepted), and an optional period inside the bold.
Those known forms cover existing waits; new instructions always get the
structured record. It prints
`resume` only after #B is closed by a pull request merged into the default
branch. A closed issue alone is insufficient. The safety net and the full
check after a merge find waiting builders; a targeted wake finds only the
waiting tickets it names. Delivery is recorded against that wait comment's
id, so the same wait is not sent twice and a new wait can be sent again.

**Delivering a resume:** comment `launch-fleet: resume starting C for #B` on #N, then run `sh "<this skill's folder>/scripts/fleet.sh" claim N <your comment id>`. Only
`go #N` may tell its recorded builder that #B merged and to continue the
instructions in wait comment C. An older claim wins, so overlapping ticks
cannot both deliver. On success, edit your claim to `launch-fleet: resume sent
C for #B`; on a definite failure, edit it to `launch-fleet: resume failed C for
#B: <why>`. On `withdraw`, edit your claim to `launch-fleet: resume withdrawn C
for #B` and send nothing.

A claim with no outcome after 10 minutes prints `reconcile resume`. Read the
claiming thread and the builder's delivery history before any retry. Proven
delivery edits that claim to `resume sent`; a definite non-delivery edits it
to `resume failed`. A still-running or unreadable sender, or an uncertain
delivery, stays claimed and goes to the orchestrator. Never resend on a
reconcile without proving the earlier delivery did not happen.
