# Merging

A `merge` line means CI is green and the selected reviewer's `VERDICT: APPROVE at <commit>` names the current head. From the project checkout, calling the loaded skill's own `merge.py` by its absolute path (the project has no `scripts/merge.py`; its FM4 command still resolves in the checkout):

1. **Check the verdict** on GitHub: the newest record-author `VERDICT:` on the pull request names this head and belongs to the selected review claim. Missing or conflicting evidence: record `launch-fleet: merge blocked <commit>: <why>`.
2. **Admit the batch:** `fleet.sh overload merge-batch`; continue only on exit 0 with `allowed: true`.
3. **Admit the merge:** `python3 -I "<this skill's folder>/scripts/merge.py" admit <owner>/<repo> <P> <commit> <checks>`, with `fleet.md`'s required checks comma-separated. `admit:` means the merge queue re-tests it. `base rule: ...` means no queue: apply `fleet.md`'s base rule and confirm `fleet.sh every` still prints this exact `merge` line (a `re-test` line instead goes to [references/reviews.md](reviews.md)). `wait:` stops.
4. **Merge:** `python3 -I "<this skill's folder>/scripts/merge.py" merge <owner>/<repo> <P> <commit> <checks> "<the APPROVE and the plan approval it relies on>" --ticket <N>`, adding `--base-rule-checked` after step 3's base rule. It merges only that commit, never with `--admin`, reads it back and records `merge queued` or `merge blocked` itself. `merged <commit>; cost ...` is a **verified merge**, and it has posted the ticket's FM4 cost line (`launch-fleet: cost: ...`, or `cost unknown` with the reason; never zero). `pending:` means read again next wake. When a head the fleet queued leaves the queue, even right after its first enqueue, it reads `queue.py`'s verdict: `dropped; recorded <id>` (the `merge dropped` record) and `waiting: <cause>` read again next wake, `re-queued; ...` queued it again once at that head after the late look still lets it merge, and a second drop, a merge conflict, a person's removal or a claimed re-queue GitHub never shows is `merge blocked`; queue facts it can't read or that disagree, and a removal whose enqueue doesn't read yet, are `pending:`. Pass the project's private flow files after `--` when it has them.
   `held: ask-due`, `held: look-due` or `held: changes-asked` means the late look holds a user-visible spec's final merge, with nothing written: do [references/reviews.md](reviews.md), "The late look". Every other merge, and a spec whose answer is `no` or absent, flows as above.
5. **Close the ticket** if its `Closes #<N>` line didn't. A refused or blocked merge whose branch conflicts goes to the builder (merge `main` in, never rebase); anything else goes to the orchestrator. Never retry a refused merge as another account.

**The landed comment** (feedback-loop contract v1, #1848): on a verified merge in any `openwizdev` repository, `merge.py` (and `settle`, through its cost) follows each closed `openwizdev/OpenWiz` issue's report link to its feedback report and posts the contract's `Landed: ...` comment there once, naming the fix as `<owner>/<repo>#<n>`, read back; it adds `; landed ...` after the cost result, and a `landed unknown:` keeps the archive row's `settle` from archiving until a later wake reads the report again and lands it, never by posting by hand. A merge that closes no linked report adds nothing.

**The ledger** (#2285): asked what a spec or the project cost, run `python3 -I "<this skill's folder>/scripts/ledger.py" <owner>/<repo> [--spec <S>] [--json]` and report what it prints: one row per merged pull request from its ticket's newest record-author cost line, then the total and the cost per merged PR over the known rows, with unknown rows counted, never as zero. Exit 1 is a failed read: report no ledger.

A move of `main` alone is never a reason to close and reopen a pull request: only the re-test guard reopens one ([references/reviews.md](reviews.md)).
