# Reviews, findings and re-tests

Read this for a `review`, `re-check`, `reconcile review`, `check review`, `findings`, `re-test`, `merge main in` or `reopen` line. Briefs come from `scripts/brief.py` (`reviewer`, `re-check`, `fresh`, `diagnose`).

## 4. Reviews and merges

A pull request is the loop's when it closes an approved ticket (its description has `Closes #<N>`) and targets the default branch. The builder hands back by pushing a commit whose subject says **green**: the check finds it there, never in a message.

**Claim it first,** for a review or a re-check alike: post `launch-fleet: review starting <commit>` on the pull request (`post.py comment`), then run `sh "<this skill's folder>/scripts/fleet.sh" claim <P> <your comment's id>`. Go on only on `go #<P>`: no older claim for that commit is live (`review starting`, `review started`, `re-check sent`), the head is still that commit, and it is still due. Otherwise edit your claim to `launch-fleet: review withdrawn <commit>`, and stop.

**Starting a review** (a `review` line, printed only once CI is green on that exact commit): start the other-family reviewer `ops-starts.py flags --repo <owner>/<repo> review_of_claude_built` or `review_of_gpt_built` prints (the models contract's cross-family rule; exit 1 means the review waits), using the branch-matching checked builder record and that exact thread's provider (unknown/conflicting family waits), as in [builders.md](builders.md), titled `Review #<P> at <short commit>`, with the brief `python3 -I "<this skill's folder>/scripts/brief.py" reviewer <PR repo>#<P> <commit>` prints. With a token service configured, that brief carries the reviewer's token step ([builders.md](builders.md), "The token step"). Then edit the claim to `launch-fleet: review started <commit>`. If CloudRoom can't start that reviewer, edit it to `launch-fleet: review refused <commit>: <reason>`: the review waits 10 minutes, as a refused start does, and is never given to another model.

### Starting a review through a host driver

Use the driver for new reviews when `host.py which` reports a chosen host other than CloudRoom. For `host: none` or `host: cloudroom`, use the CloudRoom start above. An unreadable host setting leaves the review pending. A reviewer already running keeps its original route.

After the review claim returns `go`, run the following shell block from the fleet project checkout. Supply the launch-fleet scripts directory, the pull request's repository and number, the full head, the claim comment id, the checked builder's driver harness and model id, and the Models row that builder's start was picked from, in that order. For a driver builder, use its checked private run and record-author builder status on the ticket to verify the family and match the recorded model to its configured CLI id. Use `claude` for Claude Code and `codex` for Codex. The builder's row is the one its start passed as `--row` (`Builder`, `Small builder`, `Fixer`, or `Reviewer` for a fixer on that fallback; keep it in private state with the run). With both programs on PATH, the block reads the other-family reviewer from `ops-starts.py host --repo <owner>/<repo> review_of_claude_built` or `review_of_gpt_built`, which prints its harness, model and the Models row the cross-family rule picked (`Reviewer`, or `Builder` when the Reviewer row is the builder's family), and starts it on that row. With just the builder's harness installed, it starts the same-family reviewer on the builder's own model and row. An unreadable or conflicting builder assignment, an unknown builder row or a review that waits leaves the review pending. Use the pull request number for the reviewer run and the issue number for the builder run.

```sh
set -eu
scripts=$1 repo=$2 pr=$3 head=$4 claim=$5 builder=$6 builder_model=$7 builder_row=$8
case "$builder" in
  claude) other=codex start=review_of_claude_built ;;
  codex) other=claude start=review_of_gpt_built ;;
  *) printf '%s\n' 'refused: unknown builder harness'; exit 1 ;;
esac
set -- reviewer "$repo#$pr" "$head"
if command -v claude >/dev/null 2>&1 && command -v codex >/dev/null 2>&1; then
  picked=$(python3 -I "$scripts/ops-starts.py" host --repo "$repo" "$start") || {
    printf '%s\n' 'refused: the review waits for its reviewer row'
    exit 1
  }
  harness=${picked%% *}
  rest=${picked#* }
  model=${rest%% *}
  row=${rest#* }
  if [ "$harness" != "$other" ]; then
    printf '%s\n' 'refused: the selected reviewer is not the other family'
    exit 1
  fi
  family=other-family
elif command -v "$builder" >/dev/null 2>&1; then
  harness=$builder
  model=$builder_model
  row=$builder_row
  family=same-family
  set -- "$@" same-family
else
  printf '%s\n' 'refused: the builder harness is unavailable'
  exit 1
fi
if [ -z "$model" ] || [ -z "$row" ]; then
  printf '%s\n' 'refused: the review model or its Models row is unavailable'
  exit 1
fi
brief=$(python3 -I "$scripts/brief.py" "$@")
assignment=$(printf 'launch-fleet: review starting %s\nDriver review: %s\n\n%s' "$head" "$family" "$brief")
python3 -I "$scripts/post.py" edit "$repo" "$claim" "$assignment"
python3 -I "$scripts/host.py" start "$repo" "$pr" "$harness" "$model" review-ticket --row "$row"
```

The trusted claim supplies the brief to the reviewer. After `started`, save and read back the private run map as in [builders.md](builders.md), then change only the claim's first line to `launch-fleet: review started <commit>`. For a definite refusal, record `review refused` as above. For an unknown start, keep the claim pending and reconcile from the private run map and the reviewer's GitHub status or verdict before retrying. Fresh driver reviews follow the same start steps.

For an existing reviewer named `run:<P>`, deliver a re-check with `host.py wake <owner>/<repo> <P>`. Before waking, add `Driver re-check: <family>` to the re-check claim's second line (the family recorded at start) and put the re-check brief after a blank line. After `woke`, change only the first line to `launch-fleet: re-check sent <commit>`. For a quiet driver reviewer, read its GitHub status and verdict, wake the same run once, and record `review told again` as below. If still quiet, use `host.py stop <owner>/<repo> <P>` and save and read back the run map before marking it `review given up`. Preserve the body of the edited claim. For a driver `reconcile review` line or an uncertain wake or stop, verify the saved run and trusted GitHub records before retrying, changing the claim, or starting a replacement.

**A re-check** (a `re-check` line) goes to the same reviewer: `room-cli thread tell <its thread> --mode queue --message-file <file>`, with the file holding what `python3 -I "<this skill's folder>/scripts/brief.py" re-check <PR repo>#<P> <commit> <old head> <the ids> <the answer>` prints, then edit the claim to `launch-fleet: re-check sent <commit>`. `<old head>` is the commit the reviewer's latest `VERDICT` names; `<the ids>` are the open high and medium ids its `Next:` line leaves to the builder (`none` when `main` was merged into approved work); the builder's answer is its comment since that report, one line per id (`none` if there is none). When the old head has a `launch-fleet: findings sent <old head>: review sort kept ...` record, the sort moved findings to follow-ups before the fix round: run `python3 -I "<this skill's folder>/scripts/ops-starts.py" review-sort-handoff --record "<that record>"`, pass its `recheck_ids` as `<the ids>`, and add its `reviewer_note` as the message file's last line, so the reviewer re-checks only what the builder was asked to fix and reports each moved finding as logged, never as open. They only point the reviewer at the delta: the same reviewer, the exact new head and its full re-check still apply. When the builder merges `main` into approved work, its new head is re-checked the same way. A `reconcile review` line means a claim never recorded how it went: ask the reviewer's thread whether it was started or told, and edit the claim to match, or to `launch-fleet: review failed <commit>: <why>`.

**An approach review** (a ticket whose Parent has `One-way door: yes`): when a started ticket's builder posts a comment starting `Approach note:` (its newest note is the current one) that no record author's `Approach OK: <note id>` or `Approach changes: <note id>` answers yet, claim it on the ticket with `launch-fleet: approach review starting <note id>` (`post.py comment`). Go on only if no older claim for that note is live (`approach review starting`, `approach review started`, `approach re-check sent`). An older `approach review refused <note id>` or `approach review withdrawn <note id>` is not live: a new claim retries it after the 10 minutes a refused start waits. An older `approach review starting <note id>` with no outcome is uncertain: before any retry, reconcile it from its private `approach:<N>:claim:<claim id>` key and the thread list, editing it to `approach review started <note id>` when that thread exists, or to `approach review refused <note id>: start unknown` when no key or thread does. Otherwise edit your claim to `launch-fleet: approach review withdrawn <note id>` and stop. No branch exists yet, so take the builder's family from the ticket's record-author `launch-fleet: started` record and its private `builder:<N>` thread (`records.py` finds it by its `#<N>: ` title with no branch), never the branch-matching record "Starting a review" needs; an unreadable or conflicting builder or provider waits. Start the other-family reviewer the same `ops-starts.py flags` row picks, with its family checks, titled `Approach #<N>`, with the brief `Review the approach note <note id> on <owner>/<repo>#<N> by review-ticket's "Approach review", then end your turn: you also review its pull request.` Before editing the claim to `launch-fleet: approach review started <note id>`, save `approach:<N>:claim:<claim id>` and `approach:<N>` to that thread in `LAUNCH_FLEET_STATE` and read them back; on a definite refusal edit it to `launch-fleet: approach review refused <note id>: <reason>`. A revised note after `Approach changes:` goes to the `approach:<N>` thread (`room-cli thread tell <its thread> --mode queue`), claimed and reconciled the same way, ending `approach re-check sent <note id>`. That thread is the ticket's reviewer: when its pull request's `review` line comes, claim it as usual, save `review:<P>:claim:<claim id>` and `review:<P>:<commit>` to the `approach:<N>` thread and read them back, tell it the reviewer brief the same way instead of starting another, and edit the claim to `launch-fleet: review started <commit>`; with no readable `approach:<N>` key, start a reviewer as usual. Under a host driver (one live run per ticket, the builder's), tell the orchestrator instead of starting one. A ticket without the line never gets an approach review.

**A quiet reviewer** (a `check review` line): no `VERDICT` names the head 30 minutes after its reviewer was started or asked to re-check it. The line names the reviewer's thread and the comment that records it. The reviewer gets one more try, then a fresh reviewer takes over:

1. **No verdict 30 minutes after the record:** fresh spec wakes use the GitHub and delivery checks in SKILL.md's "Each wake". Otherwise read the thread (`room-cli thread output <its thread> --all`). A tick can read and tell only the threads it started itself, so a reviewer started by an earlier tick or by the orchestrator is out of reach. When the thread is out of reach or gone, do step 2 now. Otherwise tell it again, once: `room-cli thread tell <its thread> "No report yet for pull request #<P> at <commit>. If you are still reviewing, finish and post it. If not, start now: <the brief>"`, with the brief it was given (the review brief above for `review started`, the re-check message for `re-check sent`). Then record `launch-fleet: review told again <commit>` as a new comment on the pull request.
2. **Still no verdict 30 minutes after it was told again,** or the thread is out of reach: archive the thread (`room-cli thread archive <its thread>`), so it can't post a late verdict. First retain that reviewer's immutable claim mapping for archive-only cleanup, including when this edit replaces its original start record. Then edit the comment the line names (`post.py edit`) to `launch-fleet: review given up <commit>: <why>`. If the archive failed, say so in `<why>`: the `archive` line lists the thread again when the ticket closes.
3. **The next check prints** `review #<P> for #<N> at <commit>: a fresh reviewer`: start one as in "Starting a review", the other-family reviewer `ops-starts.py flags --repo <owner>/<repo> review_of_claude_built` or `review_of_gpt_built` prints, verified from the branch-matching `start checked` record and that exact thread's provider; unknown/conflicting family waits, never another model. A reviewer span recorded as `review given up` is never told again or asked to re-check, at any commit in that span.

**The report** is the latest comment on the pull request that starts `VERDICT: APPROVE at <commit>` or `VERDICT: CHANGES at <commit>`, with the full 40-character commit. It counts only for the commit it names, and only an `APPROVE` naming the current head approves. No report, a timeout, an error or a report on an older commit is never approval.

**Review sort (before routing a `CHANGES` verdict):** runs only on `CHANGES` verdicts (never on `APPROVE`, `re-test`, `merge` or `decision`). Read the project's setting with `python3 -I "<this skill's folder>/scripts/ops-starts.py" review-sort --repo <owner>/<repo>` (from `docs/agents/fleet.md`, `Review sort: Gemini Neon Low` or `off`; one-line revert: set `Review sort: off`). If it prints `off` or exits non-zero, skip the sort and use today's path below without blocking. When it prints spawn flags (for `Review sort: Gemini Neon Low`, `--provider antigravity --reasoning-level low`), run one blind sort pass on the `CHANGES` report's findings before routing:

- **Prompt:** give the review's blocking rules (from `review-ticket`, step 3: a finding **blocks** only when a real-user path visibly breaks — `User path: <who does what ordinary thing, and what visibly breaks>` — or there is a `security`, `privacy` or `data loss` risk — `Risk: <security|privacy|data loss>: <what is at risk>`; everything else is **polish**), followed by each finding (`R1`, `R2`, …) with any `[blocking]`/`[polish]` tag stripped from its header so the sorter judges from the finding text and rules alone.
- **Output:** exactly one line per finding, `<id>: blocking` or `<id>: polish`, with no extra prose.
- **Record and routing plan:** pass the sort output to `python3 -I "<this skill's folder>/scripts/ops-starts.py" review-sort-route --repo <owner>/<repo> --pr <PR repo>#<P> --head <commit> --ids <R1,R2,...> [--already-polish <R3,...>] [--risk <R2,...>] --ticket-repo <ticket repo> --ticket <N> [--spec <S>] [--spot-check match|mismatch] [--finding-meta <json>] <sort-output-file>`. `--risk` names every open blocking finding with a `Risk:` line: only a fix round or the reviewer closes those, so the sort never moves one to polish. Leave `--spec` out for a standalone ticket (one with no parent spec): its follow-ups name the ticket itself. The sort only ever narrows a fix round, in the `Next: the builder fixes or disputes ...` row alone; it never ends a round and never approves. When `mode` is `sorted` (at least one finding stays blocking):
  1. **Record the sort on the pull request:** post its `record` with `post.py comment <PR repo> <P> "<record>"` (for example `launch-fleet: review sort <commit>: R1 blocking, R2 polish`, with `(spot-check: match)` on every 10th sort). The decision-maker and the spot-check counter read this record.
  2. **File sorted-polish follow-ups before `findings sent`:** for each entry in `follow_ups` (every finding the reviewer graded blocking that the sort called polish), run its `<review-ticket's folder>/scripts/review.py follow-up` command to file a `needs-triage` follow-up issue, and keep the issue number it prints. If any filing fails or refuses (for example, `docs/agents/triage-labels.md` is missing), fail open: take today's path below for the whole verdict, so no finding is lost.
  3. **Route from the sorted list:** send the builder `builder_message`, which carries only the sorted blocking finding ids. With no follow-up, record the plan's `findings_record` (`launch-fleet: findings sent <commit>`). With follow-ups the plan's `findings_record` is `null`: record the `findings_record` that `ops-starts.py review-sort-handoff --head <commit> --blocking <the plan's blocking ids> --filed <R3=issue,...>` prints (`launch-fleet: findings sent <commit>: review sort kept R1; follow-ups R3 #<issue>`). That record carries each finding's disposition to the next head ("A re-check", below).
- **Fallback:** `review-sort-route` returns `mode: "fallback"` with `follow_ups: []` and today's message, so take today's path below without blocking, when `Review sort` is `off` or unreadable; the sort fails, is refused, times out, or returns malformed, duplicate, unknown or missing finding lines; the sort calls a `--risk` finding polish; `the sort left no blocking finding` (with nothing to fix no new head would come, and the reviewer never reports twice at one head, so the reviewer's own labels route); or `--spot-check mismatch` says the two models disagree (`spot-check mismatch`: the disputed labels are discarded before any follow-up or fixer action). Post `record` only when it is not `null`: a mismatch's `launch-fleet: review sort <commit>: spot-check mismatch, labels discarded; revert to off`.
- **First-day spot-check:** for the first day, every 10th sort (counted from `launch-fleet: review sort` records) is also run on Claude Opus 5.5 Medium (`--provider claude-code --model claude-opus-5-5 --reasoning-level medium`) with the same blind prompt, before `review-sort-route`. Pass `--spot-check match` when both give every finding the same label, else `--spot-check mismatch`, which takes the fallback above for that verdict; then tell the orchestrator to revert by setting `Review sort: off` in `docs/agents/fleet.md`.

**Findings** (a `findings` line): read the report's `Next:` line (on its `the builder fixes or disputes` row, run "Review sort" above first), one of the review-loops contract's states: one review plus one re-check, then at most one fresh round, which never resets them. Do its row; no row asks the orchestrator to decide fix once more or log and merge. Each row ends with one record on the pull request starting `launch-fleet: findings sent <commit>`, so the line is done; a parked finding's line stays due until Jake's answer is acted on. An older report's `Next:` may still ask for the orchestrator's diagnosis: when `Next:` asks for the orchestrator's diagnosis, tell the orchestrator what `python3 -I "<this skill's folder>/scripts/brief.py" diagnose` prints; its cause and direction go into the decision.

**The fresh round** (the `fresh` row), in this order:

1. **Once per pull request.** If the oldest fresh record on it is your own `launch-fleet: fresh starting <commit>` for this head, carry on at its first step not yet done. If any other record starts `launch-fleet: fresh starting` or names a `fresh round`, never start another: tell the orchestrator, as for an unknown line. Otherwise comment `launch-fleet: fresh starting <commit>`, then read the pull request's comments again: go on only if your claim is the oldest such record.
2. **Retire, then archive, the original builder first,** resolved from private state as [builders.md](builders.md) does, so two builders never push one branch and the ticket's title finds only the fresh one. Tell it `room-cli thread tell <its thread> "A fresh builder takes over pull request #<P> for one round. Commit and push nothing more, run room-cli thread update --self --title 'Retired #<N>: <ticket title>', and end your turn."`, and end yours. On a later tick, once `room-cli thread list --include-archived --json` shows its new title, archive it (`room-cli thread archive <its thread>`) and read it back archived; keep its identity in private state. If it is out of reach, isn't retitled 30 minutes after it was told, the archive fails or you can't tell, start nothing: edit the claim to `launch-fleet: findings sent <commit>: fresh round failed: <why>`, and tell the orchestrator.
3. **Then start the fresh builder** on `ops-starts.py flags --repo <owner>/<repo> fix_round_for_claude_builder` or `fix_round_for_gpt_builder`, for the original builder's family (the models contract's fixer rule), read as for a reviewer (unknown or conflicting family, or exit 1, waits), titled `#<N>: <ticket title>`, with the brief `python3 -I "<this skill's folder>/scripts/brief.py" fresh <ticket repo>#<N> <PR repo>#<P> <branch> <commit>` prints A fleet thread starts it as its own child, as in [builders.md](builders.md); through a driver, start it on the harness, model and row `ops-starts.py host` prints for that same start ("Hosts" there), so a fixer on the Reviewer fallback runs at the Reviewer row's effort.
4. **Record it:** point the private builder mapping at the fresh builder once its start is confirmed, and check that exactly one thread titled `#<N>: ` on `<branch>` is listed, the fresh one, matching that mapping. Only then edit the claim to `launch-fleet: findings sent <commit>: fresh round started, branch <branch>`; otherwise edit it to `launch-fleet: findings sent <commit>: fresh round failed: <why>`, and tell the orchestrator. Keep both identities in private state; the ticket's `start checked` record keeps its branch, and its family is unchanged. Its green head goes to the same reviewer for the final check, as a re-check does.

**An overturned ruling whose stated cost is high:** read every new report for one, before its `findings` or `merge` line: a `- **Ruling <n>** overturned as R<m>` mark where the description's ruling `<n>` says `Cost if wrong: high`. It goes to Needs you ([user.md](user.md)), once per ruling, recorded as `launch-fleet: ruling sent to Jake <commit>: Ruling <n> as R<m>`. It does not hold the merge: the report's own line still applies.

**Jake's answer to a parked finding** comes back as one comment on the pull request, the contract's `**Orchestrator decision:** fix once more: R2 at <commit>. Why: ...` or `**Orchestrator decision:** log and merge: R2 at <commit>. Polish issues: #<n>. Why: ...`, written by a record author. On a `findings` line whose head has a `launch-fleet: parked <commit>` record, read the newest such decision that names exactly the parked findings and that head; with none, do nothing. Act on it once, while no `launch-fleet: findings sent <commit>: decision` record is there:

- **Fix once more:** tell the pull request's current builder `Jake's answer on pull request #<P> at <commit>: fix <the ids> once, as the decision <its comment link> says, then hand back a new green head.` Its new head goes to the same reviewer for a check, as a re-check does.
- **Log and merge:** tell the same reviewer `Jake's answer on pull request #<P> at <commit>: <its comment link>. Post one report at that same head that grades <the ids> as polish findings with the decision's polish issues.` Its `APPROVE` at that exact head, with CI green there, merges by the usual merge line; nothing merges on the decision alone.

Then record `launch-fleet: findings sent <commit>: decision <its comment id>: <fix once more or log and merge>`. The decision may start with an optional diagnosis, the orchestrator's choice.

If the parked report is still the latest at that head 30 minutes after a log-and-merge delivery, a `re-check` line names the parked decision. Recheck the answer and report, then post a review claim on the pull request with `launch-fleet: review starting <commit>` on the first line and `Decision retry: <decision comment id>` on the second. For a driver reviewer, keep its `Driver re-check: <family>` line second, add the decision retry line third, then put the original request after a blank line. Run `fleet.sh claim <P> <retry comment id>`. Only `go #<P>` authorizes the retry. Read the reviewer's status and report before waking the same reviewer with the original request, and wake only if it still needs the request. Leave the retry claim in place to prevent repeat delivery, including after an uncertain wake. If the report is still missing after 30 more minutes, the `look` line raises the unfinished review for the orchestrator. The replacement report and exact-head merge checks still govern the merge.

**Re-testing** (a `re-test` or `merge main in` line): the re-test guard, under M1 (#337, the #326 lesson). An approved head whose checks are green gets a `merge` line only when `main` has changed nothing it may clash with since the `main` its CI provably tested. Otherwise the check prints `re-test #<P> for #<N> at <commit>: main changed <files> in #<merge> after <time>, which its CI may not have tested; run its CI again on the latest main`.
- **What its CI tested.** Each required check counts its latest workflow run, which must be green. GitHub builds a pull request's test merge lazily, and a re-run or a reopen can reuse an old one: #258's first reopen tested a `main` three merges old. So a run's time proves nothing. A test merge is always built after its head exists, so by default the check credits the CI with `main` as of the head's commit time. After this skill's own re-test, it credits the base that run recorded ("Delivering a resume", above).
- **What clashes.** A merge into `main` since then that changed a file the pull request also changes, renames counted both ways. Or, until a map of which test reads which file exists (K15), one side changed a test file (under `tests/`, `test/`, `spec/`, `__tests__/` or `fixtures/`; `test.sh`, `test_*`, `*_test.*`, `*.test.*`, `*_spec.*`, `*.spec.*`) and the other changed anything but docs (`*.md`, `docs/`). When two approved pull requests clash with each other in one check, only the lower number gets `merge`; the other gets its `re-test` line once that one has merged. Any other move of `main` merges as M1 allows.

1. **Claim it:** comment `launch-fleet: re-test starting <commit>` on the pull request. The check prints nothing more for this head while no new run has started, for up to 30 minutes.
2. **Start a fresh run at the same head:** `gh pr close <P>`, then at once `gh pr reopen <P>`. `reopened` is one of the CI workflow's events, so GitHub starts a new run, and the head, and so the APPROVE, stay as they are. If the reopen fails, or you can't tell, read `gh pr view <P> --json state,headRefOid` and reopen again while it is `CLOSED` at that head. A pull request left closed within 10 minutes of an unfinished claim (still `re-test starting`) gets a `reopen` line from the check, so a tick cut short strands nothing. A closure after the claim is edited to `re-test sent` or `re-test failed`, or later than that, is someone's choice, and the check leaves it closed. Never `gh run rerun`: GitHub's docs say a re-run uses "the same `GITHUB_SHA` (commit SHA) and `GITHUB_REF` (git ref) of the original event". Never delete the branch, and never merge `main` into it yourself.
3. **Record which CI run tested what:** list the head's runs, `gh run list --commit <commit> --event pull_request --json databaseId,workflowName,createdAt`. Take the one created after your claim whose jobs include every CI check `fleet.md` lists (`gh run view <run> --json jobs --jq '[.jobs[].name]'`). There must be exactly one. Other workflows, such as a changelog check, check out the same kind of merge and are never the CI run. Once one of its required jobs has finished, read that job's checkout line: `gh api --allow-escape-sequences repos/<owner>/<repo>/actions/jobs/<job id>/logs | grep -m 1 'HEAD is now at'`. It reads `HEAD is now at <short> Merge <commit> into <base>`, both full 40-character commits, and its `<commit>` must be the head. Edit your claim to `launch-fleet: re-test sent <commit> on <base> in run <run id>: <what main changed, from the line>`. The check credits that base only when every required check's latest run is that run. A run of another workflow, two runs, a short base, or no run id earns no credit, and the line comes back. No such run, or no such line, 10 minutes after the reopen: edit the claim to `launch-fleet: re-test failed <commit>: <why>`. The check then prints the line again, and a second failure is `merge blocked`.
4. **Then the check decides,** once that run is green:
   - `merge`: the run tested a `main` with every clash in it.
   - `re-test` again: `main` moved again since, in a file that clashes. Start over at step 1.
   - `merge main in #<P> for #<N> at <commit>: its re-test ran on main at <base>, without <files> in #<merge>; tell its builder to merge main in`: GitHub reused an old test merge, so a reopen can't help. Tell the builder: `Merge origin/main into your branch (never rebase), run the full set and hand back a new green head: GitHub's test merge for pull request #<P> is stale, so its re-test ran without <files> in #<merge>.` Then record `launch-fleet: merge main asked <commit>`. Its new head goes back to its reviewer for a re-check, as any new head does.

   A red new run is a `CI failed` line, for the builder, as any red CI is. A claim with no new run 30 minutes on comes back as the `re-test` line, ending `(again: no new run 30 minutes after it was claimed)`.

**The late look** (`contracts/checkpoints.v1.md`, RC3 #1831): `merge.py merge` holds the final merge of a user-visible spec (its last open planned ticket, where the spec answers `User-visible: yes` or `yes, a release`, or its answers are invalid) until the owner's look at that head's evidence is recorded. A ticket whose closing pull request is queued or merged counts as closed, so do the `merge` lines of one such spec one at a time, never in parallel; a held head that conflicts is `merge blocked`, as any conflict. `python3 -I "<this skill's folder>/scripts/merge.py" look <owner>/<repo> <P> <commit> --ticket <N>` prints the same reading and only reads. Do the row its `held:` line names; each new head starts over.

| `held:` | What the fleet does |
| --- | --- |
| `ask-due` | Take the evidence from the pull request: a preview link, screenshots or a short video of the change working, never code (no pull request, commit, file, diff or source archive). Write one or more `Evidence: <preview\|screenshots\|video> <link>` lines and one `Look for: <what the owner should see working>` line to a file, then run `python3 -I "<this skill's folder>/scripts/merge.py" ask <owner>/<repo> <P> <commit> <checks> --ticket <N> <file>`, with `fleet.md`'s required checks comma-separated, after the merge line's verdict check (step 1 of SKILL.md's "Merging"): it posts `launch-fleet: late look asked #<P> at <commit>` on the spec once per head, only while every required check is green and the head is mergeable, and refuses a code link. With no evidence to show, or on `refused:`, tell the builder to add the evidence to the pull request's description. On `ask posted <id>` or `ask already posted <id>`, tell the orchestrator the ask's link: who records the owner's look is its routing |
| `look-due` | Nothing: the owner's late-look record (`**Late look by <decider>, <date>, #<P> at <commit>:** ...`, from a record author) releases it, and the next `merge` line merges |
| `changes-asked` | Tell the builder `The owner's late look at pull request #<P> at <commit> asked for changes: read the late-look record on the spec. Make them and hand back a new green head.`, then record `launch-fleet: findings sent <commit>: late look` on the pull request; send nothing again while that record is there. The new head goes through its review and gets a new ask |

A move of `main` alone is never a reason to close and reopen a pull request: M1 (the base rule in `fleet.md`) and the checks above decide, and only "Re-testing" reopens one, for its re-test.

If any of this fails, record `launch-fleet: merge blocked <commit>: <why>` on the pull request. When `main` moved and the branch conflicts, or its merge group failed the checks (it and the latest `main` break each other), tell the builder to merge `main` in and fix it (never rebase or force-push); its new head goes back for a re-check. Otherwise tell the orchestrator.
